# エージェントと一緒に作業する

> このページは執筆前の骨組みです。設計シートとト書きだけを置き、本文はまだ書いていません(追跡: #219)。

## 設計シート

- 分類: 説明型(Diátaxis: how-to)
- 読み手: だれが / Claude Code や Codex のようなコーディングエージェントに FloatSoda の作業を任せたい人。自分ではあまりコードを書かない人を含む / 何を知っている / エージェントに依頼を出せる。FloatSoda のリポジトリの決まりは知らなくてよい / 読んで何をしたい / エージェントが規約を読み、守って作業する準備を整えたい
- 出力言語と文体の指定: 日本語。敬体(CONTRIBUTING.md の「ドキュメントのトンマナ」の「文体」)
- テーマ: エージェントに FloatSoda の作業をさせる前に、エージェントが読む入口ファイルと skill の位置を知り、作業の線を決める
- 依頼の解釈: 「エージェントを作る」ではなく「リポジトリでエージェントを使う」と読む
- テーマファイル: how-to
- Why(目的): エージェントが規約を読まないまま作業すると、ブランチ名や PR の範囲、日本語の出力などの決まりに外れた PR ができる。入口を先に教えて、差し戻しを減らす
- What(目標・結果): エージェントが最初に読むファイルと、skill の置き場所が分かる。エージェントに任せる範囲と、人間が確かめる箇所を決められる
- How(手段): 入口ファイルを確かめる → 規約の正本を確かめる → skill の位置を確かめる → 任せる範囲を決める → 作業後に人間が確かめる箇所を決める
- 要素:
  - すべてのエージェントの入口は `AGENTS.md`。Codex などはこれを直接読み、Claude Code は `CLAUDE.md` の `@AGENTS.md` を通して読む(AGENTS.md の冒頭)
  - プロジェクトの指示は `AGENTS.md` に書き、`CLAUDE.md` には書かない(AGENTS.md の冒頭)
  - 既定は「調べて説明する。コードは変えない」。依頼されたときだけ変更する(AGENTS.md の「Working Style」)
  - リポジトリのオーナーへの出力は日本語で書く。コード、識別子、パスは原文のまま(AGENTS.md の「Output Language」)
  - ブランチ名にエージェントやツールの名前を入れない(`codex/`、`claude/`、`agent/` を使わない)(AGENTS.md の「Repository Conventions」、CONTRIBUTING.md の「ブランチ名」)
  - 規約の正本は CONTRIBUTING.md(開発規約)と REVIEW.md(レビューの基準)。AGENTS.md は写さず参照する(AGENTS.md の「Repository Conventions」)
  - リポジトリの skill の正本は `.agents/skills/`。`.claude/skills/` は Claude Code 用の派生スタブで、直接編集しない(AGENTS.md の「Repository Skills」)
  - `.agents/skills/` の skill は8つ(ただし件数はページに書かない)。用途は、実機テストの生成と実行、ジュニアコーダーテスト、リリース、OpenVR API の参照など(`.agents/skills/*/SKILL.md` の description)
  - C# の解析と変更には Rider の MCP を使えるなら使う。なければ `dotnet` CLI と検索で続ける。ソフトウェアはエージェントが勝手に入れない(AGENTS.md の「Rider MCP」)
  - 変更に使った人かエージェントかによらず、規約は同じ(CONTRIBUTING.md の冒頭)
  - レビューは三層。自動(CodeRabbit)、人間・エージェントの PR レビュー、フェーズ末の Codex による監査(REVIEW.md の「9. レビューの層と分担」)

  - 手順2: 規約の正本を確かめる

  - 手順4: 任せる範囲と、人間が確かめる箇所を決める
  - うまくいかないとき
- ※要確認:
  - エージェントに最初の依頼を出すときの文例を載せるか(一次情報はない。載せるなら、オーナーが書いた例を使う)
  - Codex や Cursor など、Claude Code 以外の準備(各ツールが `AGENTS.md` を読む設定の有無)は、リポジトリに書かれていない。ページに書くなら各ツールの公式資料で確かめる
  - 開発環境のページ(dev-environment.md)に含まれるツール(Rider など)と、このページの範囲の線引き

## ト書き

### この手順でできること

- 読み手が持って来るもの: 「エージェントに FloatSoda の作業をさせたい」という目的
- このページが渡すもの: 手順が終わったときの状態(エージェントの入口、規約、skill の位置が分かり、任せる範囲を決めてある)
- 読み手がすること: 自分の状況がこのページの対象かを確かめる
- 次へ進む先: 「前提条件」

### 前提条件

- 読み手が持って来るもの: エージェントのツールと、FloatSoda のクローン
- このページが渡すもの: 手元でビルドとテストが通っていること(開発環境のページ ../3-prepare/dev-environment.md)
- 読み手がすること: 足りなければ先に開発環境を用意する
- 次へ進む先: 手順1

### 手順1: エージェントの入口ファイルを確かめる

- 読み手が持って来るもの: クローンしたリポジトリ
- このページが渡すもの: `AGENTS.md` が入口であること、Claude Code は `CLAUDE.md` から読み込むこと、指示を足すなら `AGENTS.md` に書くこと
- 読み手がすること: エージェントが `AGENTS.md` を読む状態で起動する
- できた?: エージェントに「このリポジトリの出力言語は」と聞くと、日本語と答える
- 次へ進む先: 手順2

### 手順2: 規約の正本を確かめる

- 読み手が持って来るもの: 入口ファイルを読むエージェント
- このページが渡すもの: 規約の正本が CONTRIBUTING.md と REVIEW.md にあること。ここには写さず、リンクと「書き始める前に読む」ことだけを伝える(../3-prepare/conventions.md)
- 読み手がすること: エージェントに、作業の前に2つを読ませる
- 次へ進む先: 手順3

### 手順3: skill の位置を確かめる

- 読み手が持って来るもの: 規約を読んだエージェント
- このページが渡すもの: skill の正本が `.agents/skills/` であること、`.claude/skills/` は直接編集しないこと、用途の見つけ方(各 SKILL.md の description)。skill を足す・直す手順は ../4-write/skills.md へリンクする
- 読み手がすること: 必要な skill の名前を確かめる
- 次へ進む先: 手順4

### 手順4: 任せる範囲と、人間が確かめる箇所を決める

- 読み手が持って来るもの: やらせたい作業
- このページが渡すもの: 既定が「調べて説明する」であること。コードの変更は依頼したときだけ行うこと。実機の確認はエージェントではなく人間が判定すること(実機テストの skill の役割分担)。PR の本文でエージェントが書いた箇所を、人間が確かめること
- 読み手がすること: 任せる範囲と確かめる箇所を、1つずつ決める
- できた?: 「エージェントがやること」「自分が確かめること」を1行ずつ言える
- 次へ進む先: 作業の進め方は、規約のページ(../3-prepare/conventions.md)と、PR の出し方(../5-submit/address-review.md)
- 【未決】任せる範囲の例を載せるか。載せるなら、どの作業(調査、実装、レビュー)から始めるのが無難かはオーナーの意見が要る

### うまくいかないとき

- 読み手が持って来るもの: エージェントが規約に外れた変更をした状況
- このページが渡すもの: 症状ごとの行き先。ブランチ名にツール名が入った、無関係な変更が混ざった、`.claude/skills/` を直接編集した
- 読み手がすること: 規約に照らして、エージェントにやり直させる
- 止まる箇所: 取り消せない操作(`push`、`force`)はエージェントに任せず、人間が確かめてから行う(※要確認: AGENTS.md に明記はない。オーナーの方針を確かめる)
