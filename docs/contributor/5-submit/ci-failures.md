# CI が落ちたとき

> このページは執筆前の骨組みです。設計シートとト書きだけを置き、本文はまだ書いていません(追跡: #219)。

## 設計シート

- 分類: 説明型(Diátaxis: how-to)
- 読み手: だれが / PR を出して、CI が落ちた人。コードを書く人 / 何を知っている / `dotnet build` と `dotnet test` の基本操作 / 読んで何をしたい / 落ちた原因を探し、手元で再現して、直したい
- 出力言語と文体の指定: 日本語。敬体(CONTRIBUTING.md の「ドキュメントのトンマナ」の「文体」)
- テーマ: CI が落ちたとき、どのステップで落ちたかを見て、同じ手順を手元で動かして再現し、直す
- 依頼の解釈: 「CI」はコード側の CI(`ci.yml`)を中心にし、docs サイトの検査(`docs-site.yml`)は別の節で触れる
- テーマファイル: how-to
- Why(目的): 手元で通っているのに CI で落ちると、原因の探し方が分からず待ち時間が増える。CI がやることを知って、手元で同じ手順を再現できるようにする
- What(目標・結果): 落ちたステップが分かる。手元で同じ失敗を再現し、直して CI が通る
- How(手段): 落ちたステップを特定する → 手元で同じコマンドを実行する → 原因を切り分ける(自分の変更か、環境か) → 直して push する
- 要素:
  - コード側の CI は `.github/workflows/ci.yml`。`main` への push と、すべての pull request で動く(`.github/workflows/ci.yml`)
  - 実行環境は `windows-latest`。.NET は `10.x`(`.github/workflows/ci.yml`)
  - ステップは3つ。`dotnet build --configuration Release`、`dotnet test tests/FloatSoda.Rendering.Test --configuration Release --no-build`、`dotnet test tests/FloatSoda.Test --configuration Release --no-build`(`.github/workflows/ci.yml`)
  - 手元では CI と同じ3つのコマンドを実行する。PR の前にこれを通すのは規約(CONTRIBUTING.md の「ブランチ・PRフロー」)
  - `--configuration Release` でビルドすると、Debug では出ない警告やエラーが出ることがある(※要確認: このリポジトリで実際に差が出た例があるか)
  - `EnforceCodeStyleInBuild` が有効で、ファイルスコープ namespace は `.editorconfig` の `IDE0161` でビルド時に強制される(`Directory.Build.props`、CONTRIBUTING.md の「namespace とディレクトリ」)
  - docs サイトの検査は `.github/workflows/docs-site.yml`。PR で `docs/**` か `website/**` に触れたとき、ビルドと検査を行う(`.github/workflows/docs-site.yml`)
  - CI は SteamVR を使わない。実機でしか分からない失敗は、CI では出ない(`.github/workflows/ci.yml`)
  - 実機が要る変更は、CI が通っても別途、実機で確かめる(docs 再編の決定、2026-10-16〜17。範囲の一覧は CONTRIBUTING.md の正本にまだない)
  - テストが落ちたら、まず自分の変更かを `git stash` などで切り分ける(一次情報はない。※要確認: 手順に入れるかオーナーに確かめる)
- 見出し:
  - この手順でできること
  - 前提条件
  - 手順1: 落ちたステップを特定する
  - 手順2: 手元で同じコマンドを実行する
  - 手順3: 原因を切り分ける
  - 手順4: 直して確かめる
  - docs サイトの検査が落ちたとき
  - うまくいかないとき
- ※要確認:
  - docs サイトの検査(`docs-site.yml` の `verify`)が落ちる典型の原因と、手元での再現コマンド(`website/README.md` を読んで確かめる)
  - Release と Debug で結果が変わった実例があるか
  - CI の再実行(re-run)を、コントリビューターができるか(権限)
  - 手元では通るが CI で落ちる、環境差(OS、SDK の版)の具体例

## ト書き

### この手順でできること

- 読み手が持って来るもの: 落ちた CI
- このページが渡すもの: 手順が終わったときの状態(CI が通る)と、CI が行う3つのステップ
- 読み手がすること: 自分の状況がこのページの対象かを確かめる
- 次へ進む先: 「前提条件」

### 前提条件

- 読み手が持って来るもの: 手元のクローンと、PR
- このページが渡すもの: 手元でビルドとテストが動くこと(../3-prepare/dev-environment.md)
- 読み手がすること: 足りなければ先に用意する
- 次へ進む先: 手順1

### 手順1: 落ちたステップを特定する

- 読み手が持って来るもの: PR の CI の結果
- このページが渡すもの: 3つのステップの名前と、どれが落ちたかの見方(GitHub の Checks のログ)
- 読み手がすること: 落ちたステップとエラーの最初の行を控える
- できた?: 「ビルドで落ちた」「どのテストで落ちた」を言える
- 次へ進む先: 手順2

### 手順2: 手元で同じコマンドを実行する

- 読み手が持って来るもの: 落ちたステップ
- このページが渡すもの: CI と同じコマンド(Release 構成、`--no-build`)。Debug ではなく Release で実行する理由
- 読み手がすること: 同じコマンドを実行する
- できた?: 手元でも同じ失敗が出る(再現できる)
- 次へ進む先: 再現できたら手順3、再現できなければ「うまくいかないとき」

### 手順3: 原因を切り分ける

- 読み手が持って来るもの: 再現した失敗
- このページが渡すもの: 自分の変更か、既存の問題か、環境かの切り分け方。ビルドの失敗はコードスタイルの強制(namespace とディレクトリの一致)を疑う。テストの失敗は、どのテストか、期待値と実際の値を見る
- 読み手がすること: 原因を1つ特定する
- できた?: 原因を一文で言える
- 次へ進む先: 手順4

### 手順4: 直して確かめる

- 読み手が持って来るもの: 原因
- このページが渡すもの: 直す範囲を原因に絞ること(無関係な変更を混ぜない)。バグなら、修正を戻すと落ちるテストを足すこと
- 読み手がすること: 直して、手元で3つのコマンドを通してから push する
- できた?: 手元で3つとも通り、CI も通る
- 止まる箇所: 直したくない既存のテストが落ちるとき。テストを消して通すのではなく、仕様と食い違う理由を調べる

### docs サイトの検査が落ちたとき

- 読み手が持って来るもの: `docs/` を触った PR の、docs サイトの CI の失敗
- このページが渡すもの: docs サイトの検査の存在と、見る場所(`website/README.md` へリンク)
- 読み手がすること: ログを読み、docs のリンクや形式を直す
- 【未決】docs サイトの検査の失敗を、このページで扱うか、docs の書き方のページに分けるか

### うまくいかないとき

- 読み手が持って来るもの: 手元で再現しない失敗
- このページが渡すもの: 環境差を疑う点(OS、SDK の版、ビルド構成)と、Issue に書いて相談する経路
- 読み手がすること: 差を1つずつ合わせる
- 止まる箇所: 合わせても再現しないとき。CI のログを貼って、PR で相談する
