# レビューの指摘を受けて直す

> このページは執筆前の骨組みです。設計シートとト書きだけを置き、本文はまだ書いていません(追跡: #219)。

## 設計シート

- 分類: 説明型(Diátaxis: how-to)
- 読み手: だれが / PR を出して、レビューの指摘を受けた人。初めて PR を出す人を含む / 何を知っている / PR の出し方。REVIEW.md は読んでいなくてよい / 読んで何をしたい / 指摘の重さを見分け、直すものと返すものを分けて、PR を通したい
- 出力言語と文体の指定: 日本語。敬体(CONTRIBUTING.md の「ドキュメントのトンマナ」の「文体」)
- テーマ: レビューの指摘を、重要度と blocking かどうかで見分け、直すか返すかを決めて、PR に返事をする
- 依頼の解釈: 「指摘への返し方」を、気持ちの持ち方ではなく手順として書く
- テーマファイル: how-to
- Why(目的): 指摘の重さが分からないと、全部を直して PR が膨らむか、重い指摘を見落とす。重さの基準を知って、直す範囲を決められるようにする
- What(目標・結果): すべての指摘に、直した、または理由つきで直さないという返事がある。blocking の指摘が残っていない
- How(手段): 指摘を重要度で分ける → blocking を直す → 非 blocking とスコープ外を返す → 直した差分を確かめる → 返事を書く
- 要素:
  - 指摘の重要度は8段。behavioral correctness、tree lifecycle と state transitions、incremental update correctness、public API consistency、test coverage、documentation consistency、performance、style / maintainability の順(REVIEW.md の「1. 重要度の順序」)
  - blocking にしてよいのは、重要度 1〜5 に当たり、concrete failure mode を説明できる指摘。6〜8 は原則として非 blocking の提案(REVIEW.md の「2. finding の基準」)
  - concrete failure mode を書けない指摘は、書けるようになるまで格下げされる(REVIEW.md の「2. finding の基準」)
  - スコープ外の改善要求は、「別 Issue 向け」と明示した非 blocking として伝えられる(REVIEW.md の「2. finding の基準」、「8. scope discipline」)
  - 指摘を直すために、無関係なリファクタリング、リネーム、クリーンアップ、依存の追加・削除を同じ PR に混ぜない(CONTRIBUTING.md の「PR のスコープ」)
  - バグ修正には regression test が要る。修正を戻すと落ちるかが判定基準(REVIEW.md の「5. テスト」)
  - レビューは三層。自動の入口(CodeRabbit)、人間・エージェントの PR レビュー、フェーズ末の Codex 監査。blocking の判断は人間・エージェントの PR レビューが行う(REVIEW.md の「9. レビューの層と分担」)
  - CodeRabbit は `profile: "chill"` で、`request_changes_workflow: false`。blocking の判断をしない(`.coderabbit.yaml`)
  - 既存のコードがそうなっているという理由だけで、正しい仕様とは判断されない(REVIEW.md の「2. finding の基準」)
  - 仕様が食い違うときの優先順位は、FloatSoda の明示された差異・設計判断、Flutter の仕様、既存の実装は根拠にならない、の順(REVIEW.md の「3. 仕様の一次情報と優先順位」)
  - 返し方の細かい作法(コメントの書き方、再レビューの頼み方)を定めた一次情報はリポジトリにない(※要確認)
- 見出し:
  - この手順でできること
  - 前提条件
  - 手順1: 指摘を重要度で分ける
  - 手順2: blocking の指摘を直す
  - 手順3: 非 blocking とスコープ外の指摘に返事をする
  - 手順4: 直した差分を確かめて、返事を書く
  - うまくいかないとき
- ※要確認:
  - 返事の書き方(コメントの形、再レビューの依頼の仕方)の慣行があるか。なければ、「返事を書く」の中身を最小にする
  - 指摘に同意できないときの手続き(誰が最終判断をするか)。REVIEW.md には書かれていない
  - 自動レビュー(CodeRabbit)の指摘に返事が要るか

## ト書き

### この手順でできること

- 読み手が持って来るもの: レビューの指摘がついた PR
- このページが渡すもの: 手順が終わったときの状態(blocking の指摘が残っていない、すべての指摘に返事がある)と、手順の数
- 読み手がすること: 自分の PR の状況がこのページの対象かを確かめる
- 次へ進む先: 「前提条件」

### 前提条件

- 読み手が持って来るもの: PR と、指摘のコメント
- このページが渡すもの: 手元でビルドとテストが通ること(../3-prepare/dev-environment.md)、レビューの基準の正本(REVIEW.md。../3-prepare/conventions.md から案内)
- 読み手がすること: 足りなければ先に用意する
- 次へ進む先: 手順1

### 手順1: 指摘を重要度で分ける

- 読み手が持って来るもの: 指摘の一覧
- このページが渡すもの: 8段の重要度と、blocking になる条件(重要度1〜5で、concrete failure mode がある)。基準の正本は REVIEW.md。ここには写さず、リンクと、1行の見分け方だけを書く
- 読み手がすること: 指摘を「blocking」「非 blocking」「別 Issue 向け」に分ける
- できた?: すべての指摘が3つのどれかに入っている
- 次へ進む先: 手順2

### 手順2: blocking の指摘を直す

- 読み手が持って来るもの: blocking の指摘
- このページが渡すもの: 直す範囲を指摘に絞ること(無関係な変更を混ぜない)。バグ修正なら、修正を戻すと落ちる regression test を足すこと
- 読み手がすること: 直して、テストを通す
- できた?: 手元で CI と同じ手順が通る
- 次へ進む先: 手順3
- 止まる箇所: 指摘に同意できないとき。concrete failure mode が本当にあるかを、再現コードで確かめてから返事をする

### 手順3: 非 blocking とスコープ外の指摘に返事をする

- 読み手が持って来るもの: 残りの指摘
- このページが渡すもの: 非 blocking は、直すか、直さない理由を書く。別 Issue 向けは、Issue を立てるか、立てないと決めたことを書く
- 読み手がすること: 指摘ごとに返事を書く
- できた?: 返事がない指摘が残っていない
- 次へ進む先: 手順4

### 手順4: 直した差分を確かめて、返事を書く

- 読み手が持って来るもの: 直した差分
- このページが渡すもの: 差分が指摘への対応だけであること、PR 本文の欄(Tests、Scope / follow-up)を更新すること
- 読み手がすること: 差分を確かめ、PR に直した旨と変更点を書く
- できた?: PR 本文が今の差分と合っている
- 次へ進む先: CI が落ちたとき(../5-submit/ci-failures.md)

### うまくいかないとき

- 読み手が持って来るもの: 指摘の意味が分からない、または同意できない状況
- このページが渡すもの: 症状ごとの行き先。意味が分からない → 指摘の根拠(どの入力で何が壊れるか)を聞く。同意できない → 再現コードで確かめる
- 読み手がすること: 該当する行き先を選ぶ
- 止まる箇所: 判断が割れるとき。PR のコメントで相談する
