# 決定を ADR に書く

## この手順でできること

議論で決まった内容を、あとから「なぜそう決めたか」を読める形で ADR(Architecture Decision Record、設計の決定の記録)に書けます。手順が終わると、ADR が1本、置き場所にある状態になります。ADR には、背景、決定、理由、影響が書かれます。Flutter との差異なら、差異の記録に必要な5項目も書かれます。

決定の理由が議論のコメントにしかないと、あとから「なぜこうなっているか」を追えません。同じ議論も繰り返されます。ADR は、その理由を repo に残すための記録です。ADR の正本は repo に置きます。

手順は5つです。

1. ADR に書く決定かを確かめる
2. 番号と置き場所を決める
3. 背景・決定・理由・影響を書く
4. Flutter との差異なら、5項目を足す
5. PR で出す

議論の結論が出ていない場合は、先に [提案を書く](write-proposal.md) へ戻ってください。

## 前提条件

次の2つがそろっていれば、手順1から始められます。

- 決まった内容と、議論の Issue を確認しておくこと
- 提案の書き方と規約を読んでおくこと([提案を書く](write-proposal.md)、[コントリビューターの規約](../3-prepare/conventions.md))

## 手順1: ADR に書く決定かを確かめる

次のような決定は、ADR に書きます。

- 設計判断
- 依存やプロジェクト構成の決定
- Flutter との差異
- public API の方針

typo の修正のように、設計判断のない変更は書きません。迷ったら書いてください。Issue が必須な変更([CONTRIBUTING.md](../../../CONTRIBUTING.md) の「Issue が必須な変更」)のうち、設計判断を伴うものが目安です。

<!-- ※要確認: ADR に書く決定の線を定めた一次情報がリポジトリにない。上は CONTRIBUTING.md の「Issue が必須な変更」を目安にした仮の案で、ADR の対象と Issue が必須な変更が一致するかは確かめていない。確かめるには、オーナーに対象の線を確認する -->

**できた?** 「書く」「書かない」のどちらかを、理由とあわせて言えます。書くなら手順2へ進みます。

## 手順3: 背景・決定・理由・影響を書く

ADR には、次の4つの欄を書きます。

| 欄 | 書くこと |
| :-- | :-- |
| 背景 | 決める前の状況 |
| 決定 | 選んだもの |
| 理由 | 選ばなかった案と、選んだ理由 |
| 影響 | 決めたことで生じる制約や代償 |

議論の記録を見ながら、欄ごとに書きます。

<!-- ※要確認: ADR の見出しの形式と、状態(proposed、accepted、superseded)を使うか。ここでは4欄だけを案内した。確かめ方: オーナーの決定を待つ -->

**できた?** 理由の欄に、実際に検討した案と選んだ理由が書かれています。別の案を検討していない場合は、その旨が書かれています。

## 手順4: Flutter との差異なら、5項目を足す

> 【未決】この節は判断が要るため、ト書きのまま残しています。オーナーが決めたあとで本文にします(追跡: #219)。

- 読み手が持って来るもの: Flutter と違う設計の決定
- このページが渡すもの: 記録必須の5項目と、ADR の欄との対応。差異を固定するテストの名前を書くこと。利用者に見える差異は、利用者向けの docs にも書くこと
- 読み手がすること: 5項目を ADR に書く
- できた?: 5項目がすべて埋まり、テストが実在する
- 止まる箇所: 台帳(`known-divergences.md`)にすでに同じ差異のエントリがあるとき。重複させず、どちらを正にするかをオーナーに確かめる(移行は後回し)

Flutter と違う設計の決定には、記録必須の5項目を書きます(REVIEW.md の「6. Flutter parity」)。

| 項目 | ADR の欄との対応 |
| :-- | :-- |
| Flutter の挙動 | 背景 |
| FloatSoda の挙動 | 決定 |
| 差異が必要な理由 | 理由 |
| 差異を固定するテスト | 影響(テストのファイルとメソッド名を書く) |
| 利用者に影響する場合のドキュメント | 影響(利用者向けの docs へのリンクを書く) |

差異を固定するテストがない差異は、次の移植で戻されます。テストの名前を必ず書いてください。利用者に見える差異は、利用者向けの docs にも書きます。

差異の台帳 [known-divergences.md](../../../.agents/skills/floatsoda-device-test-gen/references/known-divergences.md) に同じ差異のエントリがあるときは、重複させないでください。どちらを正にするかを、Issue でオーナーに確かめます。台帳を ADR にまとめる移行は、まだ決まっていません。

**できた?** 5項目がすべて埋まり、テストが実在します。

</details>

## 手順5: PR で出す

PR には ADR の追加だけを入れます。関連する Issue は、PR 本文の「Related Issue」欄に `#NN` の形で結び付けます。この PR だけで Issue の完了条件を満たすときは、`Closes #NN` と書きます。出したあとの指摘への対応は [レビューの指摘を受けて直す](../5-submit/address-review.md) に進んでください。
