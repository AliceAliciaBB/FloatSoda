# 提案を書く

> このページは執筆前の骨組みです。設計シートとト書きだけを置き、本文はまだ書いていません(追跡: #219)。

## 設計シート

- 分類: 説明型(Diátaxis: how-to)
- 読み手: だれが / 新しい機能や設計の変更を提案したい人。Flutter と違う設計にしたい人を含む / 何を知っている / FloatSoda の使い方と、Issue の立て方。受け入れの基準は知らなくてよい / 読んで何をしたい / 提案が受け入れ範囲に入るか確かめ、理由を読み手(利用者のペルソナ)に照らして書いて、Issue として出したい
- 出力言語と文体の指定: 日本語。敬体(CONTRIBUTING.md の「ドキュメントのトンマナ」の「文体」)
- テーマ: 提案を、受け入れ範囲の確認、ペルソナへの照らし合わせ、Flutter との差異の記録の3点を押さえて Issue に書く
- 依頼の解釈: 提案が通ったあとに決定を ADR に書く手順は、別ページ(決定を ADR に書く)に分ける
- テーマファイル: how-to
- Why(目的): 受け入れ範囲の外の提案や、理由の書かれていない提案は、議論に入る前に止まる。必要な情報を先に書いて、議論を設計の中身に使えるようにする
- What(目標・結果): 提案の Issue が1件立っている。受け入れ範囲に入ること、どの利用者のどの困りごとを解くか、Flutter と違うなら理由が書かれている
- How(手段): 似た議論を探す → 受け入れ範囲を確かめる → public API なら受け入れ条件を確かめる → ペルソナに照らして書く → Flutter との差異を書く → Issue を出す
- 要素:
  - 現段階のコアが受け入れるのは、Flutter の `widgets/basic.dart` 相当のプリミティブ層のウィジェット。装飾済み・複合ウィジェットや、Material/Cupertino 相当のコンポーネントは受け入れない(CONTRIBUTING.md の「受け入れ範囲」)
  - 範囲外の貢献は、コア以外の別パッケージやユーザーランドでの実装を検討する(CONTRIBUTING.md の「受け入れ範囲」)
  - 新しい public API の合否基準は、更新後の docs だけを読んだ LLM が、その API を正しく使えるか(CONTRIBUTING.md の「新しい public API を追加する場合の受け入れ条件」)
  - public API を追加・変更する PR は、マージ前にジュニアコーダーテストを通す。手順はスキル `floatsoda-junior-coder-test` にある(CONTRIBUTING.md の「新しい public API を追加する場合の受け入れ条件」)
  - 想定する作り手は3種類。LLM にコードを書かせる VRChatter、Booth でオーバーレイを売るクリエイター、uGUI を避けたいエンジニア(AGENTS.md の「Target Users」)。提案はこの3種類のどれの困りごとを解くかで説明する
  - 「コードに書けない状態」(外部のアセットや設定ファイル)を入れる提案は、トレードオフを検討する(AGENTS.md の「Target Users」)
  - Issue が必須な変更は、public API の追加・変更・削除、observable behavior の変更、アーキテクチャ・依存関係・構成の設計判断、Flutter parity / divergence に関する判断、breaking change を伴う変更(CONTRIBUTING.md の「Issue が必須な変更」)
  - Flutter と違う設計にするときは、記録必須の5項目(Flutter の挙動、FloatSoda の挙動、差異が必要な理由、差異を固定するテスト、利用者に影響する場合のドキュメント)を書く(REVIEW.md の「6. Flutter parity」)
  - 「実装しやすい」「こちらの方が安全」「こちらの方が自然」だけでは、差異の理由にならない(REVIEW.md の「6. Flutter parity」)
  - 差異のラベルは `flutter-divergence` を付ける(CONTRIBUTING.md の「タイトルとラベル」)
  - breaking change の有無は、PR 本文に必ず書く。Alpha は判定を省略する理由にならない(CONTRIBUTING.md の「PR のスコープ」)
  - 似た議論は Issue の検索で探せる(docs 再編の決定、2026-10-16〜17)
  - 機能要望のテンプレートは `.github/ISSUE_TEMPLATE/feature_request.yml`(中身は※要確認)
- 見出し:
  - この手順でできること
  - 前提条件
  - 手順1: 似た議論を探す
  - 手順2: 受け入れ範囲に入るか確かめる
  - 手順3: 利用者のペルソナに照らして、困りごとを書く
  - 手順4: Flutter と違う設計なら、差異の5項目を書く
  - 手順5: Issue を出す
  - うまくいかないとき
- ※要確認:
  - `.github/ISSUE_TEMPLATE/feature_request.yml` の欄(読んで、欄ごとの書き方を対応づける)
  - ペルソナ(3種類)の正本は AGENTS.md の「Target Users」。前の docs の `TargetUsers.md`(退避済み)の移し先が未定なので、リンク先をどこにするか
  - 提案が通る・通らないを決める人と手続きの一次情報(CONTRIBUTING.md にはない)
  - 提案を出す前に、Issue で設計方針をすり合わせることを求めている領域(スクロール系、ポインタ接続など)の最新の扱い(ページには状況を書かない)

## ト書き

### この手順でできること

- 読み手が持って来るもの: 作りたい機能や変えたい設計の案
- このページが渡すもの: 手順が終わったときの状態(提案の Issue がある)と、提案に書く3点(受け入れ範囲、ペルソナ、Flutter との差異)
- 読み手がすること: 自分の案がこのページの対象かを確かめる
- 次へ進む先: 「前提条件」

### 前提条件

- 読み手が持って来るもの: 案と、GitHub のアカウント
- このページが渡すもの: FloatSoda の方針を知っていること(../1-get-involved/values.md)、Issue の読み方(../3-prepare/read-github.md)
- 読み手がすること: 足りなければ先に読む
- 次へ進む先: 手順1

### 手順1: 似た議論を探す

- 読み手が持って来るもの: 案のキーワード
- このページが渡すもの: Issue と PR を検索する場所と、閉じた Issue も見ること。古い Issue だけを根拠に決めないこと
- 読み手がすること: 似た議論を探し、見つかれば内容を読む
- できた?: 似た議論が「ある」か「ない」かを言える
- 次へ進む先: ない、または新しい論点があれば手順2

### 手順2: 受け入れ範囲に入るか確かめる

- 読み手が持って来るもの: 案の中身
- このページが渡すもの: 受け入れ範囲(プリミティブ層)の判断の仕方と、範囲外のときの行き先(別パッケージやユーザーランド)。public API なら、LLM が正しく使えるかが合否になること。正本は CONTRIBUTING.md(../3-prepare/conventions.md から案内)
- 読み手がすること: 範囲に入るかを、正本で確かめる
- できた?: 「入る」「入らない」「迷う」のどれかを言える
- 止まる箇所: 迷うとき。Issue で相談する
- 次へ進む先: 手順3

### 手順3: 利用者のペルソナに照らして、困りごとを書く

- 読み手が持って来るもの: 範囲に入る案
- このページが渡すもの: 3種類のペルソナと、提案をどれに照らすかの考え方。書くのは「だれの、どんな困りごとを、この提案がどう解くか」の3点
- 読み手がすること: 困りごとを3点で書く
- できた?: ペルソナを1つ挙げて、その人の困りごとを一文で言える
- 次へ進む先: 手順4(Flutter 由来の部品の場合)、そうでなければ手順5

### 手順4: Flutter と違う設計なら、差異の5項目を書く

- 読み手が持って来るもの: Flutter と違う設計にしたいという案
- このページが渡すもの: 記録必須の5項目と、理由にならないもの。Flutter の元の実装の読み方は移植のページ(../4-write/port-from-flutter.md)へリンクする。提案が通ったら、決定を ADR に書く(../6-propose/write-adr.md)
- 読み手がすること: 5項目を、分かる範囲で書く
- できた?: 理由が「実装しやすい」「自然」だけになっていない
- 次へ進む先: 手順5

### 手順5: Issue を出す

- 読み手が持って来るもの: 3点(と、必要なら5項目)を書いた下書き
- このページが渡すもの: 機能要望のテンプレートと、ラベル(種別、領域、`flutter-divergence`)。breaking change の有無を書くこと
- 読み手がすること: テンプレートに書いて出す
- できた?: Issue が立ち、種別ラベルが1つ付いている
- 次へ進む先: 議論で決まったら、決定の書き方(../6-propose/write-adr.md)

### うまくいかないとき

- 読み手が持って来るもの: 提案が止まった状況
- このページが渡すもの: 症状ごとの行き先。範囲外と言われた → 別パッケージの案。理由が足りないと言われた → 手順3と手順4
- 読み手がすること: 該当する手順に戻る
- 止まる箇所: なし
