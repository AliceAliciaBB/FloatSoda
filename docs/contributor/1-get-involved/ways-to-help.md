# どんな貢献が助かるか

> このページは執筆前の骨組みです。設計シートとト書きだけを置き、本文はまだ書いていません(追跡: #219)。

## 設計シート

- 分類: 説明型(Diátaxis: explanation)
- 読み手: だれが / FloatSoda に関わりたい人。VRChatter、ドキュメントや動作検証で関わりたい人、コードを書く人 / 何を知っている / FloatSoda の名前。コードを書けなくてもよい / 読んで何をしたい / 自分の得意なことが、どの貢献になるかを知り、始める入口を選びたい
- 出力言語と文体の指定: 日本語。敬体(CONTRIBUTING.md の「ドキュメントのトンマナ」の「文体」)
- テーマ: 貢献は5種類(ドキュメント、動作検証、コード、提案、skill)あり、どれから始めてもよい
- 依頼の解釈: 「今どれが足りないか」ではなく「どんな種類が助かるか」と読む。今の状況は Issue のラベルに任せる
- テーマファイル: explanation
- Why(目的): コードを書けない人や初めての人は、自分の関わり方がないと思って手を引く。種類を示して、入口を見つけられるようにする
- What(目標・結果): 5種類の貢献と、それぞれに要るものが分かる。どの種類から始めてもよいと分かる
- How(手段): 5種類を同じ形(何をする / 要るもの / 次に読むページ)で並べる。動作検証は「落ちた / 落ちなかった」の報告がいちばん助かる理由も書く
- 要素:
  - 貢献は5種類。ドキュメントを書く、動作検証をする、コードを作る・直す、機能を提案する、エージェント向けの skill を書く(docs 再編の決定、2026-10-16〜17)
  - 動作検証では「落ちた / 落ちなかった」の報告がいちばん助かる。SteamVR は環境で挙動が大きく変わるため。落ちなかった報告も、その環境で動いた記録になる(docs 再編の決定、2026-10-16〜17)
  - 実機のチェックは、HMD・GPU・プラットフォーム・モード・日付を名前に含む jsonl に結果を残す(`.agents/skills/floatsoda-device-test-run/SKILL.md`)
  - ドキュメントの変更は、`docs/` 配下のファイルに対して行う。Wiki 側を直接編集しても同期で上書きされる(CONTRIBUTING.md の「ドキュメントを更新する場合の注意」)
  - コードの貢献の受け入れ範囲は、現段階ではプリミティブ層のウィジェット(CONTRIBUTING.md の「受け入れ範囲」)
  - 提案は Issue で出す。public API の追加には受け入れ条件がある(CONTRIBUTING.md の「新しい public API を追加する場合の受け入れ条件」)
  - skill の正本は `.agents/skills/`(CONTRIBUTING.md の「エージェント向け skill を追加・変更する場合」)
  - 手が足りない箇所は `help-wanted`、始めやすい Issue は `good-first-issue` のラベルで探せる(CONTRIBUTING.md の「タイトルとラベル」)
  - 今どの貢献が足りないかは、このページに書かず、Issue のラベルに任せる(docs 再編の決定、2026-10-16〜17)
  - 5種類のどれから始めてもよい。コードを書かなくても関われる(docs 再編の決定、2026-10-16〜17)
- 見出し:
  - どの貢献から始めてもよい
  - ドキュメントを書く
  - 動作検証をする
  - コードを作る・直す
  - 機能を提案する
  - エージェント向けの skill を書く
  - 次に読むページ
- ※要確認:
  - 動作検証の報告を受け取る場所(Issue か、サンプルの `checks/results/`)が決まっているか(report-bugs.md の【未決】と同じ)
  - ドキュメント貢献の入口になる文書(執筆の規約、文体の規約)が、新しい docs のどこに置かれるか。前の docs の `WritingDocumentation.md`(退避済み)の移し先が未定
  - 各種類に「要るもの」として書く前提(例: 動作検証は HMD)のうち、HMD がなくてもできる動作検証があるか

## ト書き

### どの貢献から始めてもよい

- 読み手が持って来るもの: 「自分でも関われるのか」という不安
- このページが渡すもの: 貢献が5種類あること、コードを書かなくても関われること、どの種類から始めてもよいこと。今の状況(何が足りないか)はここに書かず、Issue のラベルで探すこと
- 読み手がすること: 5種類の名前を見て、気になるものに進む
- 次へ進む先: 5つの節のうち、読み手が選んだもの

### ドキュメントを書く

- 読み手が持って来るもの: 分かりにくかった箇所、直したい箇所
- このページが渡すもの: ドキュメントが `docs/` にあること、直す場所の考え方、要るもの(Git と GitHub、書く規約の案内)
- 読み手がすること: 自分が直したい箇所が、この種類に当たるか確かめる
- 次へ進む先: 規約のページ(../3-prepare/conventions.md)。文体の規約の正本は※要確認

### 動作検証をする

- 読み手が持って来るもの: HMD と SteamVR のある環境
- このページが渡すもの: 「落ちた / 落ちなかった」と環境を報告するのがいちばん助かる理由(SteamVR は環境で挙動が変わる)。落ちなかった報告も記録になること
- 読み手がすること: 自分の環境で動く確認が、この種類に当たるか確かめる
- 次へ進む先: 不具合の報告と動作検証の報告(../1-get-involved/report-bugs.md)

### コードを作る・直す

- 読み手が持って来るもの: 手元でビルドとテストを通せる環境
- このページが渡すもの: 受け入れ範囲(プリミティブ層)、Issue が要る変更の種類、書き方の入口
- 読み手がすること: 自分の変更が受け入れ範囲に入るか確かめる
- 次へ進む先: 開発環境(../3-prepare/dev-environment.md)、Flutter からの移植(../4-write/port-from-flutter.md)

### 機能を提案する

- 読み手が持って来るもの: 作ってほしい機能や、設計の変更の案
- このページが渡すもの: 提案が Issue で始まること、提案が通る条件の案内
- 読み手がすること: 提案したい内容が、この種類に当たるか確かめる
- 次へ進む先: 提案を書く(../6-propose/write-proposal.md)

### エージェント向けの skill を書く

- 読み手が持って来るもの: 繰り返す作業を、エージェントに任せたいという目的
- このページが渡すもの: skill の正本が `.agents/skills/` であること、足す・直す手順の入口
- 読み手がすること: 自分の目的が skill に当たるか確かめる
- 次へ進む先: skill を足す・直す(../4-write/skills.md)

### 次に読むページ

- 読み手が持って来るもの: 選んだ貢献の種類
