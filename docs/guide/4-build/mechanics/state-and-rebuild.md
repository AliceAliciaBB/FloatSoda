# 状態と作り直し

> このページは執筆前の骨組みです。設計シートとト書きだけを置き、本文はまだ書いていません(追跡: #219)。タイトル案: 値が変わると、画面が変わる仕組み

## 設計シート

- 分類: 説明型(Diátaxis: explanation)
- 読み手: だれが / Booth クリエイター(uGUI の経験者)、uGUI を避けたいエンジニア、AI に頼む VRChatter、React や Flutter のような宣言的 UI を触ってきた人。チュートリアルの段2で `SetState()` を使った / 何を知っている / `text.text = ...` のように画面の部品を直接書き換える考え方 / 読んで何をしたい / `SetState()` で何が起きるのか、なぜ値を直接書き換えても画面が変わらないのかを理解したい
  - 共通の性質と専門用語の扱い: CONTRIBUTING.md の「ドキュメントのトンマナ」の「読み手」
- 出力言語と文体の指定: 日本語。敬体。トンマナは CONTRIBUTING.md の「ドキュメントのトンマナ」に従う
- テーマ: ウィジェットは作り直される不変の設計図で、状態は `State` が持ち、`SetState()` が作り直しを予約する、という考え方
- 依頼の解釈: 1つの部品の中の状態の話に絞る。ツールの全体を画面と状態に分ける話は、「画面と状態の分け方」へ分ける
- テーマファイル: explanation
- Why(目的): 値を直接書き換えても画面が変わらない理由が分からないと、AI の書いたコードの直し方が分からず、同じ失敗を繰り返す
- What(目標・結果): `SetState()` を呼ぶと、画面が次のフレームで作り直される。作り直されるのは変わった部分だけと分かる
- How(手段): uGUI との違い → ウィジェットと State の分担 → `SetState()` の中で起きること → よくある失敗、の順に説明する
- 要素:
  - ウィジェットは不変の `record` で、画面の設計図にあたる(`src/FloatSoda/Widgets/Widget.cs`、`README.md`)
  - 状態は `StatefulWidget<T>` に対応する `State<T>` が持つ(`src/FloatSoda/Widgets/ComponentWidget.cs`)
  - `SetState(Action)` は、状態を変える処理を実行し、その Element に再構築を要求する(`src/FloatSoda/Widgets/ComponentWidget.cs`)
  - 再構築は即座には行われず、`BuildOwner` が次のフレームで dirty な Element を親から順に作り直す(`AGENTS.md` の「Widget/Element Tree」、前の docs の「BuildPipeline」)
  - 作り直した結果は、変わった部分だけがレイアウトと描画をやり直す(`AGENTS.md` の「RenderObject Tree」)
  - 同じ型と同じ `Key` のウィジェットは、Element が使い回される(`AGENTS.md` の「Widget/Element Tree」)
  - 値の変化がペイントだけで済むとき、`FadeTransition` のように `SetState()` なしで描画だけを更新する部品がある(`src/FloatSoda/Widgets/Animation/FadeTransition.cs`)
  - 失敗の例: `SetState()` を使わずにフィールドを書き換えると、画面が変わらない(`samples/FloatSoda.Samples.OverlayApp/CounterWidget.cs` の `SetState(onPressed)` と対比)
  - `InheritedWidget` は、祖先の値が変わると依存する子孫を作り直す(`AGENTS.md` の「Widget/Element Tree」)
  - uGUI は部品を直接書き換える方式で、FloatSoda は状態を変えて作り直す方式(前の docs の「TargetUsers」)
- 見出し:
  - 値を直接書き換えても、画面は変わらない
  - ウィジェットは作り直される設計図で、状態は State が持つ
  - SetState を呼ぶと、次のフレームで何が起きるか
  - 作り直しても、変わった部分だけが描き直される
  - SetState を使わない更新がある
  - 作り直しが期待どおりに起きないとき
- ※要確認:
  - `SetState()` を `Build()` の中や、別のスレッドから呼んだときの挙動(`src/FloatSoda/Elements/BuildOwner.cs` を読んで確かめる)
  - `Key` を付けた子の並べ替えで State が保たれること(`CHANGELOG.md` の #276 を読み、テストで確かめる)
  - uGUI の語彙への対応表(`Update`、`SetActive` など)を足すか(「uGUI から来た人へ」と重なるため、リンクで済ませるか決める)

## ト書き

### 値を直接書き換えても、画面は変わらない

- 読み手が持って来るもの: `text.text = ...` のように、部品を直接書き換える経験
- このページが渡すもの: 冒頭の問い。フィールドを書き換えても画面が変わらないコードの例と、その理由を知らないと困ること
- 読み手がすること: 自分の経験との違いを確かめる
- 次へ進む先: 次の節

### ウィジェットは作り直される設計図で、状態は State が持つ

- 読み手が持って来るもの: 前の節の問い
- このページが渡すもの: ウィジェット(不変の設計図)と `State`(変わる値)の分担
- 読み手がすること: どの値をどちらに置くかの考え方をつかむ
- 次へ進む先: 次の節

### SetState を呼ぶと、次のフレームで何が起きるか

- 読み手が持って来るもの: ウィジェットと State の分担
- このページが渡すもの: `SetState()` が再構築を予約し、次のフレームで親から順に作り直される流れ(図1枚)
- 読み手がすること: 呼んだ直後には画面が変わらないことを知る
- 次へ進む先: 次の節

### 作り直しても、変わった部分だけが描き直される

- 読み手が持って来るもの: 作り直しの流れ
- このページが渡すもの: 作り直しが毎フレームの全描画ではないこと。深い仕組みは、コントリビューター向けの解説へのリンクで渡す
- 読み手がすること: 作り直しを恐れなくてよい理由をつかむ
- 次へ進む先: 次の節

### SetState を使わない更新がある

- 読み手が持って来るもの: 作り直しの仕組み
- このページが渡すもの: `FadeTransition` のように、描画だけを更新する部品があること。「アニメーションを付ける」へのリンク
- 読み手がすること: 使い分けをつかむ
- 次へ進む先: 次の節

### 作り直しが期待どおりに起きないとき

- 読み手が持って来るもの: 画面が変わらない、または意図しない状態のリセット
- このページが渡すもの: よくある原因(`SetState()` の呼び忘れ、`Key` の付け忘れ)と、ガイドの「5. 困ったとき」の「反応しないときに切り分ける」へのリンク
- 読み手がすること: 自分のコードの原因を探す
- 止まる箇所: なし
- 次へ進む先: 「画面と状態の分け方」
